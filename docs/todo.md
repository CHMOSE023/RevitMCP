## 1. F13 · 双文档工作流实测（**优先**）

**欠的是什么。** `expectedDocumentId` 这套防串文档的机制目前只有单元测试覆盖，
从没在"同时开着两个模型"的真实环境里跑过。而那正是它唯一的存在理由：
用户在 Revit 里切了活动文档，而调用方手里还攥着上一个文档的 ID 继续写。
单元测试能验的是"ID 不匹配时会拒绝"，验不了的是
**主线程上那次重新核对到底拿到的是不是当时真正的活动文档**——
管线里为此专门做了一次"入队时检查一遍、上了主线程再检查一遍"，
这个双重检查从来没有被真实的文档切换触发过。

**为什么没做。** 需要人在 Revit 里开第二个 `.rvt` 并在验收过程中手动切换活动文档，
现有的 `workflows/*.ps1` 都是"一个文档、从头跑到尾"的形态，没法自动化这一步。

**做的话要什么。**
- 第二个模型（`MCPModelTest_B.rvt` 之类，随便什么内容，有个标高就行）
- 一个新工作流 `workflows/m10-multidoc.ps1`，中途停下来提示用户切文档
- 至少覆盖三种情形：
  1. 带**正确**的 `expectedDocumentId` 写 A —— 应当成功
  2. 带 **A 的** `expectedDocumentId`、但用户已切到 B —— 应当拒绝，且**一个字节都没写**
  3. **不带** `expectedDocumentId` 写 —— 当前行为是落到活动文档（B）。
     这一条要确认的是"默认行为是否可接受"，不是"是否报错"

**验收标准**：情形 2 之后，A 与 B 两个文档的构件数都与调用前一致。

## 2. F14 剩余 · 能力补齐

前三条（载入族、导出取景、房间竖向约束）已在 M10-E 做完。剩下：

| 项 | 说明 | 难点 |
|---|---|---|
| 原生楼梯 / 栏杆 | 目前只能靠 `escape_hatch` 绕 | Revit 的楼梯 API 跨版本差异大，2019 与 2022+ 不是一条路 |
| 材质层补全 | 材质能赋、层构造不能改 | `CompoundStructure` 的读写是另一套模型，工作量接近一个新工具族 |
| 交付质量汇总 | "这批模型建得合不合格"的一次性体检 | 要先定义"合格"，而那取决于交付标准，不是技术问题 |

**为什么没做。** 这三条是**功能缺口，不是缺陷**——没有它们，已有的工具不会给出错误结果，
只是有些活干不了。而前面修的都是"调用成功、模型不对"那一类，优先级不在一个量级。

三条里工作量最小、收益最直接的是**材质层补全**：墙已经能建、材质已经能赋，
差的只是层构造，缺口最窄。要动就从它开始。

## 3. F10 剩余 · 上下文成本（客户端侧那一半）

服务端那一半已在 M10-G 做完（`textBlock` 三档）。剩下的都在客户端侧：

- **结果去重**（报告 §6 第 1 条）—— 同一构件在多次查询里重复出现。服务端改不了。
- **字段投影 / `countOnly` / 游标分页** —— `revit_get_element_parameters` 仍是最大的
  单条回执来源。它已有 `nameContains`，但默认返回全部参数的**原始值 + 显示值**。
  要收窄得先想清楚哪一种能安全省掉：写参数要原始值，读给人看要显示值，两个都不能一概去掉。
- **运行时渐进启用工具集** —— 分组已经做好（`enabledToolsets` 静态生效），
  缺的是运行时按需开关。**受协议限制**：本服务是无状态 HTTP，没有 server→client 通道，
  发不出 `listChanged`，客户端不会主动重新拉 `tools/list`。

**为什么没做。** 用户 2026-09-20 明确搁置（"运行时渐进启用先不做"）。

**更该走的路**：客户端侧的 `defer_loading` + `tool_search_tool_*`。
那是第一等的渐进发现——在客户端层面就不把 65 KB 的 `tools/list` 全塞进上下文，
"schema 超过约 10K token 就回本"。本服务 75 个工具、65 KB，早就过线了。
它不需要服务端改任何代码，只需要接入方配置。
