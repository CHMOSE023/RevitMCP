# 设计草案 · 工具集分组与渐进式发现

> 状态：**草案。第 5 节（分组与静态启用）已实现，第 6、7 节待定。**
> 起因：74 个工具的 `tools/list` 是每个会话的固定开销，且还在变大。

---

## 1. 先量，别猜

本会话抓的真实 `tools/list`（69 个工具，比现在少 5 个，比例不变）：

| | |
|---|---:|
| 整份 `tools/list` 紧凑 JSON | **65,316 字符** |
| 其中描述 + schema | 55,367 字符 |
| 单个工具中位数 / 均值 | 608 / 802 字符 |
| 最大的 10 个工具占 | **38.9%** |

最大的那几个全是几何创建类：`create_annotations` 2803、`transform_elements` 2679、
`create_surface_based_elements` 2399、`create_line_based_elements` 2288、`create_views` 2051。
它们大不是因为话多（描述只占一两百字符），而是**schema 深**。

## 2. 按专业分组能省多少：**很少**

按建筑 / 结构 / MEP 分组，实际能摘掉的只有：

| 分组 | 工具数 | 字符 | 占比 |
|---|---:|---:|---:|
| 建模/通用 | 18 | 19,369 | 35.0% |
| 出图 | 17 | 15,222 | 27.5% |
| 文档/查询 | 25 | 15,042 | 27.2% |
| 协同/审计 | 7 | 3,465 | 6.3% |
| **MEP** | **2** | **2,269** | **4.1%** |

**纯专业切法的上限是 MEP + 协同 ≈ 10%。**

原因值得说清楚：**这套工具是按几何范式组织的，不是按专业**——
`revit_create_line_based_elements` 同时造墙（建筑）和梁（结构），
`revit_create_point_based_elements` 同时造门窗（建筑）和结构柱（结构）。
专业的边界横切在工具内部，切不开。

## 3. 真正能省的是**功能**这条轴

按下面第 5 节的分组实际算一遍（69 个工具的真实 schema 尺寸 × 源码里的分组标注）：

| 会话类型 | 启用的集合 | 工具数 | 省 |
|---|---|---:|---:|
| 只审计 / 只查询 | core | 23 | **−72.9%** |
| 只建模，不出图 | core + 建筑 + 结构 | 27 | **−59.7%** |
| 只出图 | core + 出图 | 40 | **−46.3%** |
| 建模 + 出图（最常见的完整会话） | core + 建筑 + 结构 + 出图 | 44 | **−33.2%** |
| 不碰 MEP | 摘掉 MEP 2 个 | 73 | −4.1% |

最后一行就是"按专业切"的全部收益。前四行才是这件事值得做的理由。

所以分组应当**以功能为主轴、专业为副轴**，并且允许一个工具属于多个集合
（`create_line_based_elements` 同时属于 `modeling.architecture` 与 `modeling.structure`）。

## 4. schema 去重：另一条独立的路

点结构（`x`/`y`/`z` 三个属性 + 各自的描述）在整份 schema 里被展开了 **28 次**，
约 5,936 字符 ≈ **9.1%**。JSON Schema 的 `$defs` + `$ref` 能把它收成一份定义 + 28 个引用，
省下约 8%，**对所有会话都生效、与分组无关**。

**但本批不做。** `SchemaGenerator` 当初明确写了"不支持 `$ref`，直接截断"——
不是疏忽，是因为**各家客户端与模型侧对 `$ref` 的支持程度不一致**，
schema 展不开的后果是整个工具不可用，比多花 8% 的上下文严重得多。
要做得先验证目标客户端确实能解析引用，再开。

## 5. 分组与静态启用（**已实现**）

### 分组

一个工具可以属于多个集合。`core` 永远启用，不可关闭。

| 集合 | 内容 |
|---|---|
| `core` | 文档与查询、标高轴网、类型与族、参数、几何、警告、保存、删除、建模指引、操作状态 |
| `modeling.architecture` | 墙门窗楼板屋顶、房间、载入族 |
| `modeling.structure` | 梁柱基础（与建筑共用几何工具，同时挂在两个集合下） |
| `modeling.mep` | 风管水管线管桥架、MEP 系统 |
| `documentation` | 视图、图纸、注释标记、明细表、取景、导出 |
| `coordination` | 链接、工作集、阶段、设计选项、碰撞、同步、修订 |
| `authoring` | 材质、类型编辑、项目参数、编组、变换 |
| `escape` | 两个逃生舱（另有独立开关，见 README） |

### 启用

配置 `enabledToolsets`（默认全开，行为与今天完全一致）：

```json
{ "enabledToolsets": ["core", "modeling.architecture", "documentation"] }
```

没启用的工具**不注册**——既不出现在 `tools/list`，调用也返回"工具不存在"。
这样才是真的省：只从清单里藏起来、却还能调，等于给调用方留了一个看不见的陷阱。

`revit_list_toolsets`（只读、常驻 `core`）列出所有集合、各自的工具数与启用状态，
让调用方知道"还有哪些能力没打开"，而不是以为服务就这么点本事。

## 6. 运行时渐进式启用（**待定**）

设想：`revit_enable_toolset({ name: "modeling.mep" })` → 之后 `tools/list` 多出那几个。

两个必须先讲清楚的问题：

1. **推不了 `listChanged`。** 2026-07-28 的 modern era 移除了 GET 流与会话，
   服务端**没有反向通道**能主动通知客户端"工具列表变了"。
   所以 `capabilities.tools.listChanged` 只能保持 `false`，
   靠工具回执里那句"已启用 N 个工具，请重新调用 tools/list"让 Agent 自己重列。
   激进缓存工具列表的客户端会看不到新工具——这一条必须写进契约，不能假装它是标准的渐进式发现。

2. **它是全局状态。** 本服务是无会话的：A 客户端启用了 MEP，B 客户端也会看到。
   单客户端场景没问题，多客户端同连一个 Revit 时就是互相影响。

因此**建议先只做第 5 节的静态启用**，观察真实使用里"中途需要临时能力"的频率，
再决定值不值得引入一个会互相影响的全局开关。

## 7. 网关式单入口（**不建议**）

即只暴露 `revit_find_tools` + `revit_invoke` 两个工具，其余靠参数派发。

省得最多，但代价是**把这套工具最值钱的部分拆掉了**：

- 每个工具的 `inputSchema` 不再参与客户端与模型侧的校验——参数错误从"调用前被拦下"
  变成"调用后由服务端报错"；
- `readOnlyHint` / `destructiveHint` 失效，客户端再也无法对删除类操作单独弹确认；
- 模型要先学会一套嵌套调用约定，而它对原生工具调用本来就更熟练。

这套服务的立身之本是"工具说得清楚、错得明白"。为了省上下文把它换成一个万能入口，
省下来的那点 token 会以更多的失败调用还回去。
